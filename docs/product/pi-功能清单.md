# Pi 功能清单

这份清单回答一个问题：**Pi 这个产品到底有哪些功能。**

用平常话写，按用户能感知的领域分类。工程记号（功能 ID、文件行号、类型名）不在这里，它们在
`pi-feature-inventory.md`（英文，给工程和校验用）。

**每项功能具体怎么用**，见 `pi-使用说明.md`——按命令行、交互界面、会话、工具、扩展、模型、RPC、SDK
分节，含前置条件、最小用法、限制与降级。

**基准**：`earendil-works/pi` 的 `086c32e7`。所有内容都是从这个固定版本的源码里读出来的，不是凭印象写的。

## 怎么读这份清单

每一项后面的标记表示**我们的确认程度**，不是功能的好坏：

| 标记 | 含义 |
| --- | --- |
| ✅ | **已确认**：从源码里逐条读出，成员可以机器重新生成并校验 |
| 🟡 | **部分确认**：知道有这个东西，但还没逐项查完 |
| ⚠️ | **有坑**：移植时容易做错，下面会说清楚错在哪 |
| ❌ | **查不到**：这个基准版本里没有可查的证据（不等于功能不存在） |

**看到 🟡 请当作「还没查完」，不要当作「查完了只有这些」。** 这份清单目前**尚未通过独立校验**，
校验完成后标记会再更新一次。

## 怎么自己重跑校验（**以及它证明不了什么**）

```bash
cd pi-go
python3 tools/gen-feature-ids.py --pi-repo /path/to/pi \
        --check-providers tools/expected-providers.txt
python3 tools/test_gen_feature_ids.py     # 抽取器自身的负向控制
python3 tools/check-doc-counts.py --pi-repo /path/to/pi   # 文档里的数字必须和生成器一致
python3 tools/mutation-sweep.py           # 故意改坏抽取器，测试必须变红（较慢）
```

**退出码 0 说明的只有这些：**
1. 固定版本 `086c32e7` 可读，且读的确实是这个提交（符号引用和短 SHA 会被拒绝）；
2. 抽取器没有触发自己的守卫——没有无法归类的调用、没有 ID 撞车、没有成员数与权威来源不符；
3. **厂商这一类**与一份独立维护的期望清单（`tools/expected-providers.txt`）**集合完全相等**。

**它证明不了的（同样重要）：**
- ❗ **除厂商、扩展钩子、思考等级、快捷键之外的其余各类，没有与另一份独立权威清单做集合比对**。它们是「重跑同一个抽取器 +
  抽取器内部守卫」——能抓住源码变动和自相矛盾，**但抓不住「抽取器和我们同时漏掉了同一个东西」**。
- ❗ 它**不替代逐文件独立遗漏审计**（该审计尚未完成），**也不证明这 28 类没有漏项**。

所以退出码 0 的正确读法是「**没有发现不一致**」，不是「**已证明完整**」。

工具只读固定版本，不看你本地 pi 仓库的当前状态，所以结果不会因为谁拉了新代码而变。

## 一、命令行

**四种运行形态** ✅
- **交互式**：完整终端界面
- **打印**：跑一次、输出结果就退出
- **JSON**：把过程以 JSON 逐行输出，给程序消费
- **RPC**：常驻，接命令、发事件

⚠️ **形态是运行时按终端状态决定的，不只看参数。** `--mode` 只接受 `text`/`json`/`rpc` 三个值；
`text` 的实际结果取决于**标准输入和标准输出是不是终端**——在终端里得到交互式，一旦被重定向（比如接管道）
就自动变成打印模式。

说准确一点（避免误读）：**没有 `--mode interactive` 这个写法**，参数只认 `text`/`json`/`rpc`；
但交互式**是能通过参数走到的**——`--mode text` + 两端都是终端 + 没加 `--print`，解析结果就是交互式。
也就是说：**不是「参数到不了交互式」，而是「没有哪个参数值叫交互式」。**

**40 个命令行参数** ✅ —— 覆盖：选模型与厂商、指定或追加系统提示词、会话（继续/恢复/新建/指定目录/
分叉）、工具开关与白黑名单、思考等级、扩展与技能与提示词模板与主题的加载或禁用、打印与导出、
主题、审批开关、离线模式等。

**22 个斜杠命令** ✅ —— `settings` `model` `scoped-models` `export` `import` `share` `copy` `name`
`session` `changelog` `hotkeys` `fork` `clone` `tree` `trust` `login` `logout` `new` `compact`
`resume` `reload` `quit`

## 二、会话

**会话是一棵树，不是一条线** ✅ —— 可以从任意历史位置分叉（`fork`）、原地复制（`clone`）、在分支间
导航（`tree`）。

**五种「换会话」操作**：新建、恢复、分叉、克隆、导入 ✅

⚠️ **换会话不是「改个指针」，而是一整套拆卸重建。** Pi 会：先问扩展要不要取消 → 对旧的扩展实例发关闭
通知 → **把扩展全部卸载重装** → 再发启动通知。**扩展可以否决整个操作**，这也是为什么这几个操作会返回
「成功了，但什么都没做」。移植时如果只换状态、让扩展继续活着，扩展会带着过期数据继续跑，而且**不报错**。

**上下文压缩**（会话太长时自动或手动 `compact`）✅
- 触发条件：上下文超过「模型窗口减去预留额度」（预留默认 16384，可配置）
- 保留最近约 20000 token 的原文，更早的内容换成摘要
- ⚠️ **压缩不删任何历史**。它只是改变「发给模型的那份投影」，原始记录仍在会话里。移植时用「删消息」
  实现压缩，会**隐形地**丢掉历史——因为模型看到的下一次请求长得一模一样。
- ⚠️ **绝不能在「工具结果」处切断**：工具调用和它的结果必须留在一起。只按 token 预算切，早晚会切开。
- ⚠️ **摘要本身要花钱**，并计入会话总量。别把压缩当成零成本操作。

**分支摘要** ✅ —— 离开一个分支时，Pi 会把「你正在放弃的那条线」摘要后注入你要去的分支。
⚠️ **文件记录是累积的**：读过/改过哪些文件，会跨多次压缩和嵌套摘要不断累加。只按当前窗口统计，
**第一次看起来完全正确，第二次就丢历史**。

**导出与分享** ✅ —— 导出 HTML 或 JSONL、导入 JSONL、分享为私密 GitHub gist、复制最后一条回复。

## 三、工具

**7 个内置工具**（模型可调用）✅ —— `bash` `edit` `find` `grep` `ls` `read` `write`

另有一套**独立的 4 个工具**用于底层 harness（`bash` `edit` `read` `write`）✅ ——
⚠️ 这是**两套不同的工具集**，不是一套，harness 那套没有 `find`/`grep`/`ls`。

**并发规则** ✅ —— 一批调用默认并行；**只要其中有一个工具声明「不能并发」，整批都改成串行**。
⚠️ 顺序是可观察的契约：并行时「先全部开始、结束按完成顺序、结果按原始顺序」；串行时「一个走完再下一个」。

⚠️ **`edit` 的每处修改都对照原始文件匹配，且禁止重叠**——不是依次作用在改动后的文件上。

✅ **工具会影响系统提示词**：每个工具都往提示词里贡献一段说明，**启用哪些工具就改变了模型看到的输入**。

## 四、扩展

Pi 的扩展能力比「插件」更深——很多地方是**可替换的接缝**，不只是通知。

**扩展一共能挂 33 个钩子** ✅ —— 覆盖会话生命周期、模型切换、思考等级变化、每条消息与每次工具执行、
压缩与分支摘要、厂商请求前后、项目信任、资源发现、用户 shell 命令、输入改写等。

⚠️ **这个数不能靠数「事件类型」得出**：事件负载类型只有 25 个，因为**一个负载类型服务多个钩子**
（整个会话家族共用一个）。按 25 算会漏掉 8 个必须实现的钩子。也不能按「每行一个」去数——
有几个钩子的声明**跨了多行**，而跨行的那几个恰好是**可以否决操作**的那几个。

**能拦截或改写的** ✅
- ⚠️ **工具参数可以被就地改写，且不会重新校验**。（pi-go 目前只支持「放行/拒绝」，**不支持改写**——这是
  一处已知能力缺口。）
- **可以否决**：换会话、分叉、压缩、树导航
- ⚠️ **bash 后端可以整体替换**——官方例子是**把命令送到另一台机器上用 SSH 执行**。也就是说 shell 不是
  内置死的，而是一个接缝。
- ⚠️ **用户输入会经过五步流水线，扩展钩子不在第一位**：先匹配扩展命令（命中则钩子**根本不触发**）→
  钩子 → 技能展开 → 模板展开 → 交给模型。**钩子看到的是原始文本**，技能和模板都还没展开。
- **项目信任**：第一个给出「信任/不信任」的扩展**说了算**，并压制内置提示。项目本地扩展在信任确定前
  **不会被加载**。

**能提供内容的** ✅ —— 注册新工具、注册斜杠命令、贡献技能/提示词/主题的搜索路径、自定义渲染、
改写 Markdown、往会话里追加自定义条目。

**85 个官方扩展示例** 🟡 —— 覆盖 Git 检查点、权限门、SSH、状态栏、通知、子代理编排、
甚至在终端里跑 WASM 游戏。**尚未逐个对应到功能条目**，所以标为部分确认。

## 五、模型与厂商

**40 个内置文本厂商** ✅ + **1 个图像厂商** + **1 个测试用假厂商**
（涵盖 Anthropic、OpenAI、Google、Bedrock、Azure、各类网关与国内厂商等）

**认证** ✅（契约部分）+ 🟡（各厂商流程细节）

已盘完并可机器校验的三组：
- **凭据只有 2 种**：API key、OAuth。
- **登录时会向你提的问题只有 4 种**：输入文本、输入密文、从列表里选、手工粘贴授权码。
- **登录过程会通知你的事件只有 4 种**：提示信息、打开这个网址、设备码（含验证地址）、进度。

⚠️ **一个容易误判的地方**：某些厂商登录时会让你「选认证方式」（比如 Bedrock 让你选
「Bearer token / AWS profile / 现有 AWS 凭据链」）——**这些是那个厂商登录流程内部的选项，不是全局的认证方式**。
把它们当成认证方式清单来数，就会得出错误的结论——统计厂商时最容易踩这个坑。

⚠️ **两个移植会踩的点：**
- **「手工粘贴授权码」这个提示可能正在和本地回调服务器赛跑**：哪边先成功，另一边就被取消。
  「取消一个提示」和「取消整个登录」是两种不同范围，混成一个的话，输掉那边会一直卡在等输入。
- **刷新 token 是在凭据存储的锁里做的**，所以多个并发请求**不会把同一个已轮换的 token 重复刷新**。
  放到锁外面：测试时看不出问题，并发时会把凭据搞坏。

🟡 **还没查完**：7 个厂商各自的 OAuth 流程细节（都建立在「设备码」和「PKCE」这两种机制之上）。

❌ **「Pi 支持多少个模型」在这个基准版本里查不到。** 模型清单是**构建时生成**的，没有提交进仓库。
仓库里只有生成器。所以任何「支持 N 个模型」的说法都需要另找证据源，不能靠数文件。
（图像模型是提交进去的：45 个。）

**思考等级** ✅ —— 7 档（关闭 / 最小 / 低 / 中 / 高 / 超高 / 最大），可按等级配置 token 预算。

⚠️ **两层重试**：厂商层重试（同一次请求内）和会话层自动重试（**重新发起整个请求**）。
两者对扩展可见性不同——会话层重试会让相关钩子**再触发一遍**。

## 七、其它

**49 个设置项** ✅ —— 压缩、分支摘要、重试、终端与图像显示、思考预算、Markdown 渲染、
默认模型与厂商、队列模式、主题、外部编辑器、shell 路径与前缀、包与扩展与技能与主题的来源、
遥测与分析开关等。

**环境变量** ✅ —— 一共 **26 个名字**，但要按**用途**分四类看，混成一类就会算错：

| 用途 | 个数 | 含义 |
| --- | --- | --- |
| **读取**（当配置用） | 21 | 程序去读这个变量来决定行为 |
| **写给子进程** | 5 | 执行 bash 命令时塞进子进程环境 |
| **写在自己身上** | 4 | 改本进程的环境，之后启动的一切都继承 |
| **先删掉** | 5 | 写给子进程之前先清掉，防止串到上一次的值 |

（合计 35 个「用途条目」但只有 26 个名字——**有些名字身兼两职**，比如 `PI_MODEL`/`PI_PROVIDER`
既写给工具、也被评测入口读取；`PI_OFFLINE` 既被读取、也被 `--offline` 写在自己身上。）

⚠️ **这里有一个「错得很像对的」陷阱**：把四种用途合成一类「读取」，会得到 24 这个看起来合理的数字——
因为那 5 个会话变量（`PI_SESSION_ID` 等）是**通过「删除」和「写入」出现的、根本没有被读取**，
却会被算成读取并被这样描述。所以必须按用途分开。
并且**「先删再写」这个配对是被程序检查的**：只写不删，生成工具直接报错。

和官方文档对照（两个方向）：
- **官方文档写了、代码里不读的：3 个**——就是上面那 5 个里的三个，它们属于「写给子进程」，不是「读取」。
  不是幽灵变量，是**角色不同**。
- **代码在读、官方文档没写的：9 个**。其中 2 个是真产品功能：`PI_EXPERIMENTAL`（开实验特性）、
  `PI_OAUTH_CALLBACK_HOST`（改 OAuth 回调主机）；其余是调试/性能开关和评测目录。
- `PI_MODEL`/`PI_PROVIDER` 属于**「名字有文档、但有一个用途没写」**——文档只说了写给工具，没说评测入口也读它。
  把这两个算成「未文档化的名字」，9 就会被吹成 11。

⚠️ **写入不限于 `PI_` 开头**：产品还会设置 `AI_AGENT=pi`。只按 `PI_` 扫会漏掉它，而英文盘点文档里
列着它——**源码和文档就对不上了**。（读取仍限定在 Pi 自己的命名空间：那些文件还读了约四十个终端/系统变量
如 `TERM`、`HOME`，那是 Pi **消费**的输入，不是它**拥有**的功能。这个边界是一个明确的取舍。）

⚠️ **「先删再写」只在该管的地方管**，有两套机制，一视同仁就会误报：
- **最终环境**（对象本身就是子进程环境，从继承来的环境拷贝而来）——**必须先删**，因为写入是有条件的，
  不写的那次会让继承来的旧值留下；
- **覆盖层**（一个空对象，事后合并到继承环境之上）——**不用删**，赋值本身就覆盖了。

检查的**不是**「名字集合是否相等」（那会让 A 处的删除替 B 处的写入担保，也放过「先写后删」），
**也不是「同一个文件里」或「名字拼写相同」**——两个函数里各自的 `env` 是两个不同对象。

**判断依据是「同一个对象」**：用 TypeScript 解析器把每处访问归到**声明它的那个绑定**。
这里有三条作用域规则必须成立，少任何一条都会把写入归错对象：
- **函数参数、解构名、catch 变量都是绑定**，所以内层的 `env` 会遮蔽外层；
- **一个绑定遮蔽的是整个作用域**，不只是它声明之后的部分——写在 `const env = …` **上面**的 `env.X`
  指的仍是那个绑定，所以名字要在遍历函数体**之前**先登记好；
- **`var` 是函数作用域**，在块里声明、出了块仍然可见，而 `let`/`const` 不是；
- **`for` 头部也是声明**（写在一个裸的声明列表里、不是语句里）——只认语句形式就会漏掉
  `for (let env = …)`／`for (const env of …)`，循环体里的写入会被归到同名的外层对象。

然后要求：**同一对象上、更早的位置删过这个名字**。

**而且有三种状态、不是两种**：如果一个对象的来源**判断不出来**（从参数、从属性展开而来），
那它既不算「有义务」也不算「免除」——**直接让工具报错**，因为「判断不了」不等于「不用做」。
如果连 receiver 都解析不到绑定，这个名字仍会计入成员，但**明确标注「检查不为它背书」**，
并把这类访问的**数量写进权威说明**里，让这个界限看得见、而不是被默认忽略。

⚠️ **两个坑（移植必看）：**
- **配置目录和会话目录这两个变量名不是固定的**，而是用「产品名」拼出来的
  （`${产品名大写}_CODING_AGENT_DIR`），产品名来自 `package.json`，默认 `pi`。
  **换个品牌名就变成 `TAU_CODING_AGENT_DIR`。写死 `PI_` 会让改名功能悄悄失效。**
  （唯一例外：终端界面那个包自己写死了字面量和 `~/.pi/agent`，改名后这两处会不一致。）
- **读法有四种**：`process.env.X`、`process.env["X"]`、从**传进来的 env 对象**上读，以及经由一个辅助函数读。
  只扫第一种会漏掉两个**官方文档写了**的变量。

**终端界面快捷键 47 个** ✅ —— 编辑器 23 · 通用输入 4 · 列表选择 6 · 全屏浏览 14。
⚠️ **要数「动作」不是「按键」**：有的动作**出厂就没绑按键**（历史记录上下翻就是），有的动作绑了多个键。
按键去数会漏掉没绑的、又把多键的重复算。这一项**有两个权威**（接口声明和默认表），程序会检查两者一致。

**终端界面的公开接口有两种算法** ✅／⚠️ —— 主入口明确列出 **133 个名字**
（68 个值 + 64 个类型 + 1 个「来自依赖、无法判定」）；
但这个包**没有 `exports` 映射**、且把编译产物整个发布，所以**技术上任何模块都能被直接引用**。
⚠️ **用哪个当对齐基准，是一个还没定的产品决策——这份文档不替你定。**
目前**发出**的是「主入口那 133 个」，因为集合总得有个权威才能存在，这个选择可以改。

**我们的建议及理由**：以主入口为基准，把更宽的那层记为**打包风险**而不是功能——
那是打包方式带来的可达性、不是设计意图；把它当基准会让 Go 版被迫连模块布局一起复刻。
**另一种选择的后果也如实说**：若以发布产物为基准，则每个编译模块的导出都算在内，
Go 版要为**这个包从未宣传过的名字**承担接口稳定性，而且数字也不是 133。
真要定，顺便还要定 pi-go 自己是否发布 `exports` 映射——那才是让这个问题消失的做法。
⚠️ 顺带发现一个真限制：`fuzzyMatch`（函数）和 `FuzzyMatch`（类型）**只差首字母大小写**，
我们的 ID 规则会把它们算成同一个——所以**值和类型分成两个集合**（TypeScript 本来就有两套命名空间）。

⚠️ **一个名字占据哪些空间必须由类型检查器判断，不能看导出写法**（而且可以同时占据多个）：
`interface Foo {}` 加 `export { Foo }` 导出的是**类型**，但那行写法和导出一个值完全一样。

⚠️ **这里有三件事必须分开，压成一个标签就会丢证据**：源码**自己声明的导出面**、
目标符号**实际是什么**、以及目标**是否在固定树之外**。
- `export { type Token } from "marked"` 已经声明了它是**只导出类型**——不管目标能不能解析，这都成立；
  把它归成「判定不了」等于把固定源码直接给出的证据丢掉。
- 一个符号可以**同时有多重身份**：类既是值也是类型，枚举同时是值、类型和命名空间——单一标签说不出来。
- `Marked` 是从依赖包**普通重导出**的，而 **`node_modules` 根本不在那个固定提交里**，
  所以它到底是什么**确实判定不了**；去读装好的包＝读工作目录。

**只用固定提交能得到的结论是：68 值 + 86 类型 + 1 来自依赖**——133 个名字、155 条归属。
**一个名字属于它的符号带有的每一个空间**：其中 22 个是类，同时是值和类型，两个身份都是真的。
如果每个名字只按「主要身份」记一次，公布出来的是一种分桶方式，而不是声明空间本身。
（工具的编译宿主**拒绝回退到磁盘**：只认调用方提供的文件，否则一个盘点就会开始回答
「你机器上恰好装了什么」。）
