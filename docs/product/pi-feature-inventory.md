## 2. Modes — two sets that are easy to conflate

**What the app runs as** is `AppMode` (`core/project-trust.ts:12`): `interactive` · `print` ·
`json` · `rpc`. **What `--mode` accepts** is a different, smaller set
(`cli/args.ts:11`, guarded at `:84`): `text` · `json` · `rpc`.

**Trap:** treating these as one four-item set of `--mode` literals is wrong twice over — the flag
takes three, and `json-event` belongs to neither set, being a source file name rather than a mode.

| Feature ID | Semantics | Implementation | Docs |
| --- | --- | --- | --- |
| `coding-agent.mode.interactive` | Full TUI session | `src/modes/interactive/` | `docs/tui.md` |
| `coding-agent.mode.print` | One-shot, non-interactive output | `src/modes/print-mode.ts` | `docs/usage.md` |
| `coding-agent.mode.json` | Emits the event stream as JSON lines | `src/modes/json-event.ts` | `docs/json.md` |
| `coding-agent.mode.rpc` | Long-lived JSON command/event server | `src/modes/rpc/` | `docs/rpc.md` |

### 2.1 The mapping — resolved at runtime from TTY state, not from flags alone

`resolveAppMode()` (`src/main.ts:118-129`) decides in this order:

| Condition | Resulting mode |
| --- | --- |
| `--mode rpc` | `rpc` |
| `--mode json` | `json` |
| `--print`, **or stdin is not a TTY, or stdout is not a TTY** | `print` |
| otherwise | `interactive` |

**`text` is never a mode.** It is the "let the environment decide" input, and the decision is made
from **terminal detection**: the same command line yields `interactive` when run in a terminal and
`print` when either stream is redirected. A port that mapped flags to modes statically would run the
interactive TUI into a pipe.

Stated precisely, so this does not contradict the table above: **there is no literal `--mode
interactive`** — the flag rejects it, since it accepts only `text`, `json` and `rpc`. But
`interactive` IS reachable through the flag: `--mode text` with both streams TTYs and `--print`
absent resolves to `interactive`. "Unreachable via `--mode`" would be wrong; the accurate claim is
that no `--mode` value *names* it.

The reverse direction exists too: `toPrintOutputMode()` (`:131-133`) maps a resolved mode back to an
output format — `json` stays `json`, everything else becomes `text`.

### 7.3 Auth — `Kind: auth`, `ai.auth.*`

**Coverage: the login CONTRACT is `enumerated`; the per-provider flows are `semantics-needed`.** The
distinction is the point — three closed sets are emitted, and none of them is "how many ways can you
log in", which the file listing invites you to answer by counting modules.

| Set | Members | Authority |
| --- | --- | --- |
| `ai.auth.type.*` | **2** — `api_key`, `oauth` | `auth/types.ts` `AuthType` union |
| `ai.auth.prompt.*` | **4** — `text`, `secret`, `select`, `manual_code` | `AuthPrompt` union |
| `ai.auth.event.*` | **4** — `info`, `auth_url`, `device_code`, `progress` | `AuthEvent` union |

**A per-provider `select` option id is NOT an auth method.** `amazon-bedrock` prompts with
`bearer-token` / `aws-profile` / `credential-chain`, and `google-vertex` with `api-key`; these are
options inside one provider's own login flow, not a taxonomy. Treating them as members is what made
a provider extraction report `api-key` and `bearer-token` as providers — the same
authority-versus-appearance error, one layer down.

**Semantics that a port gets wrong silently:**

* ⚠️ **A `manual_code` prompt may be racing a callback server.** `AuthPrompt.signal` cancels one
  pending prompt when an out-of-band event resolves the step — the callback winning aborts the
  prompt. `AuthInteraction.signal` aborts the whole flow. Two different scopes; collapsing them into
  one cancellation leaves the loser of the race waiting on input.
* ⚠️ **Refresh runs under the credential-store lock.** `Models.getAuth()` performs OAuth refresh
  inside `modify`, which is the only write path, so concurrent requests **cannot double-refresh a
  rotated token**. Refreshing outside the lock works in testing and corrupts credentials under
  concurrency.
* ⚠️ **`refresh` and `toAuth` are deliberately split**: `refresh` produces a credential, `toAuth`
  derives request auth from whichever credential ends up stored. That is what lets the store, not the
  provider, own locking. `toAuth` also covers per-credential `baseUrl` (GitHub Copilot).
* **Every provider offers `apiKey` auth, including keyless local servers** — at least one of
  `apiKey`/`oauth` must be present, and for ambient providers `resolve()` exists to report whether
  the provider is configured at all. An ambient-only provider **omits `login`**.
* **Resolution merges per field**, not per credential: `credential.key ?? env("...")` and
  `credential.env?.NAME ?? env("...")`. A port that picks "stored credential or ambient" wholesale
  produces a different result whenever only one field is stored.
* `check?` is an optional **side-effect-free** availability probe, for providers whose `resolve()`
  may run commands; absent means availability is determined by resolving auth.
* `ApiKeyCredential.env` carries provider-scoped config (Cloudflare account/gateway ids), and
  ambient AWS credentials are **detected without being copied into pi's store**.

### 11.2 The public surface has TWO defensible denominators

| | Size | What it is |
| --- | --- | --- |
| **Barrel** (`src/index.ts`) | **133 names, 155 memberships** — 68 values + 86 types + 1 external | Names the package DECLARES as its API. No `export *`, so it is enumerable |
| **Published surface** | larger | `package.json` has `main` and `files: ["dist/**/*", …]` and **no `exports` map**, so every compiled module is importable by path |

⚠️ **WHICH ONE IS THE PARITY DENOMINATOR IS AN OPEN PRODUCT DECISION.** It has not been made, and this
document does not make it. The barrel is what is currently **emitted**, because a set needs some
authority to exist at all, and that choice is reversible.

**The recommendation, with its reason, so the decision can be taken rather than defaulted into:** treat
the barrel as the denominator and record the wider surface as a packaging risk. A consumer *can*
deep-import an unnamed module, but that is reachable by an accident of packaging rather than by design,
and adopting it would commit a port to reproducing module layout as though it were contract.

**What follows from the other choice, stated fairly:** if the published surface is the denominator then
every compiled module's exports are in scope, the port owes API stability for names the package never
advertised, and the count is not 133. Whoever decides should also decide whether pi-go publishes an
`exports` map, which is what makes the question disappear.

**Three export forms all count, and missing one costs a member.** `export { X }`,
`export { type X }`, and `export type { X }`. An extractor handling only the first two returned 132
against a barrel naming 133 — the missing member was a whole-clause type export.

⚠️ **Values and types are separate sets because TypeScript has two declaration spaces.** `fuzzyMatch`
and `FuzzyMatch` are both exported and differ only in leading case, so a single flat set cannot hold
them: they normalise to one ID and the collision guard rejects the run. The split follows the
language rather than working around the naming scheme, and it is the first family where the
normalisation rule met a genuine limit.

⚠️ **The declaration space is decided by the CHECKER, not by the export syntax.** `interface Foo {}`
followed by `export { Foo }` exports a type through a clause shaped exactly like a value export.

⚠️ **Three facts are orthogonal here and compressing them into one label loses evidence.** What the
SOURCE states about the export surface, what the target symbol MEANS, and whether the target lies
outside the pinned inputs are separate questions:

* `export { type Token } from "marked"` states a **type-only surface**, and that holds whether or not
  the target can be reached. Filing it as undeterminable would discard evidence the pinned source
  gives directly.
* A symbol can carry **several meanings at once** — a class is a value and a type, an enum is a value,
  a type and a namespace — so one dominant kind cannot describe it.
* `Marked` is re-exported plainly from a bare specifier, and **`node_modules` is not in the pinned
  commit at all**, so its meanings are genuinely not determinable from the baseline. Reading the
  installed package would answer from the working tree.

The breakdown from the pinned source alone is therefore **68 values, 86 types and 1 external**: 155
memberships over 133 names, because **a name occupies every space its symbol carries**. 22 of them are
classes, which are a value and a type at once, and filing each name once under a dominant space would
publish a bucketing of names rather than the declaration spaces.

The generator's compiler host therefore **fails closed**: only files the caller supplies resolve, apart
from the compiler's own lib, which is part of the tool rather than of the pinned source. A fallback to
the file system is how a census starts answering from whatever happens to be installed.

**Classifying a re-export requires the module it comes from.** All of `packages/tui/src` is parsed as
one program for this family; with only the barrel in the program, every alias resolves to a synthetic
symbol and all 133 exports collapse into a single kind. An export that still cannot be resolved is
reported as unclassified and **fails the run** rather than being folded into a space.

**A set that cannot be enumerated is refused, not truncated.** `export * from "pkg"` re-exports a
whole surface without naming any of it, so when the target is outside the pinned inputs the checker
reports no exports for it and the barrel's list comes back short with nothing marking the gap. Every
star re-export is recorded with whether its module resolved, and an unresolved one fails this family.
This barrel has none, which is why it is enumerable at all; the guard is what keeps that a checked
fact rather than an assumption.

## 19. Hook semantics — one group, and one finding that contradicts a pi-go design position

### 19.1 ⚠️ `extension.hook.tool-call` — Pi DOES allow extensions to rewrite tool arguments

| | |
| --- | --- |
| Feature ID | `extension.hook.tool-call` |
| Kind | `hook` |
| Semantics | Fires after `tool_execution_start` and **before** the tool executes. **Can block.** `event.input` is **mutable, and mutating it in place changes the arguments the tool actually runs with.** |
| Pi evidence | `coding-agent/src/core/agent-session.ts:480-499` (`beforeToolCall` passes `input: args` by reference); `core/extensions/types.ts:901`, `:1072` |
| Docs evidence | `docs/extensions.md:751-790` |
| Coverage state | `enumerated` |

Stated guarantees (`docs/extensions.md:761-766`):
- mutations to `event.input` affect the actual execution;
- later handlers see earlier handlers' mutations;
- **no re-validation is performed after mutation**;
- blocking is `{ block: true, reason?, terminate? }`;
- `terminate` applies only to a blocked call, and the agent stops early only when **every** finalized
  result in the batch is terminating.

Ordering guarantees worth porting exactly:
- before `tool_call` runs, Pi **drains previously emitted agent events** so session state is current
  through the assistant's tool-calling message;
- in parallel mode, sibling calls from one assistant message are **preflighted sequentially, then
  executed concurrently** — so a `tool_call` handler is *not* guaranteed to see sibling results.

> **Why this matters.** pi-go's runtime currently offers a
> policy-and-denial check *only*, and its own source comment states that argument rewriting is
> deliberately not offered. That position was taken on the belief that argument rewriting was
> borrowed from another project rather than being a Pi capability. **It is a Pi capability**, in the
> source and in the docs.
>

## 20. Provider hooks — three seams inside the AI module

**Where these live matters as much as that they exist.** They fire inside the AI module, after a
provider has authenticated and serialized and just before transport — not at the boundary the
runtime calls. Leaking headers, raw payloads and HTTP responses out to the runtime would turn the
model boundary into a thin forwarding interface. They are recorded as three features served by an
**AI-module-internal hook registry**.

| | `before_provider_headers` | `before_provider_request` | `after_provider_response` |
| --- | --- | --- | --- |
| Feature ID | `extension.hook.before-provider-headers` | `extension.hook.before-provider-request` | `extension.hook.after-provider-response` |
| Semantics | Headers mutated **in place**; return value **ignored**; `null` **deletes** that header | Whole provider payload **replaced** when a handler returns non-`undefined`; chained in extension order | Observes `status` + normalized `headers` **before the response stream is consumed** |

### 20.2 There are TWO retry layers, and the hooks behave differently at each

This is the distinction that makes "once per logical request" ambiguous, and it has to be settled
before any of these rows can be read as a portable rule.

| Layer | Where | Do the hooks re-fire? |
| --- | --- | --- |
| **Provider retry** | `utils/provider-retry.ts:105` `retryProviderRequest`, used inside 6 API files | **No.** Headers and payload are transformed before the wrapper; the response hook runs after it and sees only the surviving response |
| **Session auto-retry** | `_runAgentPrompt:1063-1069` loops `while (await _handlePostAgentRun()) { await agent.continue() }`; `_handlePostAgentRun:1077-1086` → `_prepareRetry:2686-2735` | **Yes.** `agent.continue()` issues a new provider request, so preparation runs again and **every supported hook** fires again |

The session layer is the one users see as `auto_retry_start` / `auto_retry_end`. Because it re-issues rather than resumes, an extension **can** observe different headers, a
re-transformed payload and a second response across a session-level retry.

(`_willRetryAfterAgentEnd:683-696` only computes the `agent_end.willRetry` display flag — it is not
the control flow, so citing it as the mechanism is incorrect even where the conclusion holds.)

### 20.3 `before_provider_headers` — CLOSED, with that scope stated

Not adapter-dependent. `model-runtime.ts:590-608`: `prepareRequest` merges auth headers with request
headers and applies `transformHeaders` **exactly once**, before provider dispatch and after auth
resolution; the prepared options go to the provider, whose **provider-level** retries reuse them.
One common path, so no per-adapter set check is needed.

**Scope:** once per *provider request*. An extension cannot vary headers across provider-level retry
attempts. It **can** produce different headers on a session-level auto-retry, because that is a new
provider request. Stating simply that headers "cannot vary per attempt" is wrong at the session
layer.

### 20.4 Retry ordering — NOT closed for payload or response

**Three different quantities live here, so each is named explicitly:**

| Quantity | Value | Members |
| --- | --- | --- |
| Files containing the wrapper | **6** | the 5 adapters below plus `google-shared.ts` |
| APIs with provider retry | **7 / 11** | those 5 + `google-generative-ai` + `google-vertex` (both via `google-shared.ts`) |
| APIs where the **full** `onPayload → retry → onResponse` order is verified | **5 / 9 supported** | `anthropic-messages`, `azure-openai-responses`, `openai-completions`, `openai-responses`, `openrouter-images` |

The two Google APIs have provider retry but **no response hook at all**, which is why they count
toward 7 and not toward 5. For those 5 APIs the ordering is verified from the line numbers above:
the payload transform applies to every attempt, and the response hook sees only the surviving
response.

**Counted by API, not by file: provider retry covers 7 of 11.** Six files contain the wrapper, but
`google-shared.ts` serves both Google APIs, so the API set is
`{anthropic-messages, azure-openai-responses, openai-completions, openai-responses,
google-generative-ai, google-vertex, openrouter-images}`.

The **same four** APIs are outside it: `mistral-conversations`, `openai-codex-responses`,
`bedrock-converse-stream`, `pi-messages`. They have no provider-level wrapper anywhere;
`bedrock-converse-stream.ts:332` points at the session layer instead. Whether they rely on session
auto-retry alone or on a vendor SDK's own retries is *unestablished* — not proven absent.

Closure therefore reads:
- **payload hook** — provider-retry ordering closed for **7 / 11**, the same 4 outstanding;
- **response hook** — supported in 9 APIs; ordering closed for **5 / 9**
  (the 7 minus the two Google APIs, which have no response hook), the same 4 outstanding.
Until all 11 payload sites and all 9 response sites are closed, or all are shown to route through one
common wrapper, both rows stay `semantics-needed`.

> **Trap:** a single global rule inferred from two adapters is extrapolation, not closure — and a
> section cannot claim closure while admitting an open check in the same breath. **A set is closed by
> checking the set**, never by generalising from its convenient members.

### 20.5 What this means for "session truth" — a limit, not a refutation

| Layer | What it is | Mutable by hooks? |
| --- | --- | --- |
| **Session truth** | the canonical, append-only conversation record | no |
| **Provider request** | the outbound projection actually sent on the wire | **yes** — headers and whole payload |
| **Logical prompt view** | what the API reports as the system prompt | no, and it does **not** track payload edits |

Pi permits the second and third to disagree: an extension can rewrite or delete provider-level system
instructions without the reported prompt changing. "The session is the single source of truth" holds
for the conversation, and does **not** mean "what the session records is what the model received".
If exact audit or replay is ever promised, persisting the post-hook payload becomes a separate
decision.

### 20.6 pi-go gap

pi-go's AI layer has no header seam, no payload-replacement seam, and no pre-body response
observation seam. Same shape as the tool-argument-rewrite finding: a capability Pi has that pi-go
does not express. Needs a parity row and an explicit decision — implement **inside the AI module**,
or record an accepted deviation with a reason.

  - `["off"]` **exactly**, when `model.reasoning` is false;
  - otherwise `["off","minimal","low","medium","high","xhigh","max"]` filtered by the model's
    `thinkingLevelMap`: a `null` mapping removes the level, and `xhigh`/`max` are included **only if
    the map names them at all**.

  So the answer is per-model and usually shorter than the type. A port returning the union would offer
  levels the model will not honour, and one returning the five-member constant would offer them for
  every model rather than only the model-less case.

### 21.4 `prompt`, `steer` and `follow_up` acknowledge — they do not report results

Their success response carries no `data`: it is **receipt confirmation only**. The actual outcome
arrives later as events. A port that treated those responses as "the work finished" would report
completion at the wrong moment, and a synchronous client would appear to succeed instantly.

> Two nullable responses are worth porting deliberately: `cycle_model` and `cycle_thinking_level`
> return **`null`** rather than an error when there is nothing to cycle to. A port that raised an
> error there would change client behaviour for an ordinary, expected case.
>
> `{ cancelled }` on `new_session`, `switch_session`, `clone` and `fork` means the operation can
> complete successfully having done nothing, because the user dismissed a prompt. Treating success
> as "it happened" would be wrong.


## 22. Stable ID sets — for machine set-comparison

Regenerate with **`tools/gen-feature-ids.py`** (kept in this repository, reads the pinned baseline).
The sets below are its output; they are not transcribed from the tables earlier in this document.

### 22.1 Two different authorities per set

A set needs both, and conflating them produces wrong IDs:

| | Question it answers | Example |
| --- | --- | --- |
| **Membership authority** | who is a member | `builtinProviders()` returns 40 factories |
| **Name authority** | what each member is called | each provider object's own `id` field |

**A file name or a function symbol is neither.** Deriving provider names from factory symbols
produced `azure-open-a-i-responses`, `cloudflare-a-i-gateway`, `cloudflare-workers-a-i` and
`vercel-a-i-gateway` — four IDs that exist nowhere in Pi. The real names come from the `id` the
provider declares.

### 22.2 Normalization: source literal → Feature ID

Applied in this order, so a checker can reproduce it rather than infer an inverse:

1. camelCase boundary → `-` (`setStatus` → `set-status`), inserted only between a lower/digit and an
   upper character;
2. `_` → `-` (`follow_up` → `follow-up`);
3. lowercase.

**The source literal is always preserved** in a trailing comment wherever it differs from the ID, so
no consumer has to guess the reverse transform. IDs are all-lowercase by rule.

### 22.3 Reproducing and checking this section

**Prerequisites:** a Pi checkout containing the pinned commit **with its dependencies installed** —
lexing uses that checkout's own TypeScript (§22.3a). The generator is three files by concern:
`census_source.py` (pinned reads, parser-backed spans, the two views), `census_families.py` (one
extractor per family), and `gen-feature-ids.py` (emission order and exit status).

```
# regenerate the sets
python3 tools/gen-feature-ids.py --pi-repo /path/to/pi > sets.md

# regenerate AND verify the provider set against the committed expectation
python3 tools/gen-feature-ids.py --pi-repo /path/to/pi \
        --check-providers tools/expected-providers.txt
```

The Pi checkout is a required argument. Repository detection is delegated to Git itself
(`rev-parse --git-dir`) rather than testing for a `.git` directory, so a **linked worktree** — where
`.git` is a file — works. That matters because `git worktree add --detach <sha>` is the natural way
to get a pinned checkout, and both forms produce byte-identical output (verified).

**The baseline must be a full 40-character commit id**, resolved through `rev-parse --verify
<sha>^{commit}` and required to equal what was asked for. Symbolic refs and abbreviations are
rejected: `--baseline HEAD` would have read whatever a moving branch points at while still exiting
zero, quietly defeating the pin.

### 22.3a Lexing is delegated to TypeScript's own parser

Deciding what in a `.ts` file is code cannot be done with a scanner, because whether `/` opens a
regular expression or divides depends on grammatical position:

| Rule a scanner can apply | What it classifies wrongly |
| --- | --- |
| previous **character** | `return /output({ type: "x" })/;` reads as division, the regex stays visible, and its contents become an event. **18 such sites exist in the pinned source** |
| previous **token** | `if (ready) /export const createGhostTool/.test(s);` still does, because `)` ends a value when it closes a call and does not when it closes an if-head |

Both classifications are wrong in the direction that INVENTS members, and no amount of local context
settles the second, so `tools/ts-spans.mjs` asks the parser that defines the grammar. It
walks the AST for regular-expression, string and template nodes, takes comments from trivia, and
returns spans; `census_source.py` blanks them. Two consequences worth stating:

* **A template's `${}` expressions are code by construction.** The parser exposes them as ordinary
  expressions, so they are simply absent from the text spans — nothing has to remember a rule. The
  scanner versions blanked whole templates and hid a real read inside one.
* **A file that does not parse is an error, not a partial result.** Reporting spans from a file with
  syntax errors is how a subtly wrong answer would get published.

It also forces the tests to be honest: a fixture must be real TypeScript. A fixture like
`x = return /re/;` is not valid code at all and proves nothing about any construct that can appear in
the source.

⚠️ **Offsets are converted from UTF-16 code UNITS to code POINTS.** TypeScript counts code units and
Python indexes code points, so a single astral character — one emoji anywhere in a file — shifted every
later span by one per such character. The views kept the right LENGTH, so nothing looked broken; only
the content was wrong, with string delimiters blanked and following spans displaced. Emitting the
parser's offsets unchanged is a correctness bug rather than a portability detail, and the claim that
the two indexings agree was simply false.

**There is deliberately no fallback.** If Node or the checkout's TypeScript is missing the tool exits
rather than reverting to a heuristic, because the heuristic is what this replaced.

### 22.3b Published counts are checked, not maintained by hand

A figure repeated across four documents is four chances to disagree, and a reader
facing two different numbers has no way to tell which one is current — a heading
and its own body can state different totals and both look authoritative.

`tools/check-doc-counts.py` derives the figures from the generator and fails on any
disagreement — the summary row, every embedded block, the four environment role
counts with their name and membership totals, the same totals as stated in both
Chinese documents, and the test total those documents quote.

The mutation total is behind `--with-sweep` because verifying it re-runs the whole
suite once per mutation. A gate slow enough to be skipped protects nothing.

### 22.3c AST migration: what "migrated" means, and what it closes

Masking non-code is not the same as extracting structurally. A pattern over masked
text still infers membership from spelling and layout, so the families are being
moved onto the compiler API one at a time, in this order: `coding-agent.mode`, then
the thinking levels, then the discriminated unions, then the registry and
object-key families, with the TUI exports last because they need symbol resolution.

**A family counts as migrated only when `tools/check-ast-parity.py` reports an empty
set difference against the published set.** A matching count is not the test; the
members have to be the same members. The harness also lists the families it does not
yet derive, with the fact kind each still needs, because a report covering a subset
in silence reads as full coverage.

**Two failure modes this closes**, which is the argument for doing it at all:

* A member set can be **overwritten by a nested declaration** when facts are keyed by
  text name: a `Settings` interface declared inside a function occupies the same key
  as the exported one the settings family reads. Facts are taken from top-level
  statements only.
* **Declaration spaces cannot be read from export syntax.** `interface Foo {}` with
  `export { Foo }` is a type behind a clause shaped exactly like a value export, and
  one symbol can occupy several spaces at once. See §11.2.

**What the parity gate does NOT establish.** For a family whose extraction is still
pattern-based, an empty difference shows the two methods agree today — not that
either is complete. Only families listed as derived carry the stronger claim.

### 22.4 The extractor exits non-zero rather than guessing

Each row exercised, not assumed:

| Condition | Result |
| --- | --- |
| `--pi-repo` does not exist or cannot be entered | exit 2, named error, **no traceback** |
| `--pi-repo` exists but is not inside a git repository | exit 2, named error |
| `--baseline HEAD` or any symbolic ref | exit 2, "not a full 40-character commit id" |
| abbreviated SHA | exit 2, same |
| SHA absent from the repo, or resolving elsewhere | exit 2 |
| a member's name cannot be resolved | exit 1, omitted, `refusing to guess` |
| membership count ≠ resolved-name count | exit 1 |
| two literals normalize to one ID | exit 1 |
| a required source file cannot be read | exit 1, named, parsing stops immediately |
| a required source read **after** the provider check fails | exit 1, and **no success line is printed** |
| two factories declare the same provider id | exit 1, names both owning factories — checked **before** any deduplication |
| `--check-providers` file contains a repeated entry | exit 1, names the repeat |
| `--check-providers` set differs | exit 1, prints missing and unexpected members |

**A run that finds any problem never also prints a success line — including a problem found later.**
The provider check returns a verdict instead of announcing one, and the success message is printed
only after every required source has been read and every set emitted and validated.

Both halves of that were needed. Gating on the set diff alone let an expected file with duplicate
entries report the duplicate error and "no difference" together. Gating on "no errors *so far*" was
still wrong: the provider check runs before the slash-command and CLI sources are read, so a failure
after it produced a run that printed success and *then* failure. The gate is the whole run, and the
invariant is checkable — the success line appears only on exit 0.

Two of these were only reachable synthetically. The duplicate-id path cannot occur in Pi today, so
it was exercised against a purpose-built fixture repository with two factories declaring one id;
without that, "the control would catch it" is an assumption rather than a result.

### 22.5 Why the check mode exists

**Why membership must come from the registry and names from each provider's own declaration:** the
first `id:` in a provider file may belong to an authentication option, not to the provider. Taking it
yields a set of the correct size whose members are not providers — `api-key` and `bearer-token`
present, `amazon-bedrock` and `google-vertex` absent — with clean output and a zero exit, and nothing
distinguishing it from a correct run.

**Why the check compares against an independent expectation:** regenerating and diffing against the
tool's own previous output passes for any deterministic extractor, correct or not. Determinism is not
correctness. The comparison therefore runs against `tools/expected-providers.txt` inside the shipped
tool. Supplying a wrong membership exits 1 and names both the missing and the unexpected members.

Names are anchored to each provider's own `createProvider({ id })`, including the
generic-parameter call form, with a separate branch for `radius` — the one provider whose id is
caller-configurable (`providers/radius.ts:21`, `const id = options.id ?? "radius"`).

### 22.6 The event set needed three sources, and one exclusion

`coding-agent.rpc.event` is the only family whose membership spans several declarations:
`AgentEvent`, then `AgentSessionEvent` which both re-exports and extends it, then rpc-mode's own
addition. Reading any one of them alone under-counts.

**rpc-mode writes two different kinds of payload to the same stdout stream**: events, and UI
*requests* — and a request expects a reply while an event does not. Scraping everything written to stdout yields 25, because it picks up
`extension_ui_request`, which is the envelope for the nine UI methods already catalogued as
`coding-agent.rpc.ui`. Counting it here would record one surface twice.

The extractor therefore classifies rather than filters, and does so for **every** `output(` call
rather than only those whose payload fits on one line. A single-line pattern would ignore multi-line
objects, variables and helper calls entirely, so a payload added later would leave this set stale
while the run still succeeded — verified against a fixture that appends a multi-line payload: the
run now fails and names it.

Doing that exhaustively revealed **three** kinds of payload on the one stdout stream, not two:

| Kind | Form | Counted here? |
| --- | --- | --- |
| Events | literal `{ type: … }`, plus session events forwarded verbatim by `toJsonEvent` | yes (the forwarded ones via the session union) |
| UI requests | `extension_ui_request` | no — catalogued as `coding-agent.rpc.ui` |
| Command responses | built by `success`/`error`, or the awaited `handleCommand` result | no — catalogued by the response union |

Helpers and variables are classified **by name**, so a new emission form is an error rather than a
silent omission.

### 22.7 Environment variables — four role-separated sets, **35 memberships over 26 names**

A name's ROLE is part of what it is, so this axis is four sets rather than one, each with its own
authority. Merged into a single set of "reads", writes and deletions are published as reads — a
claim about the code that is the opposite of what those call sites do:

| Set | Members | Authority |
| --- | --- | --- |
| `coding-agent.environment.input` | **21** | read as configuration, in any of four read forms |
| `coding-agent.environment.exposed` | **5** | assigned into an environment object built for a child (`env.X =`) |
| `coding-agent.environment.self` | **4** | assigned onto THIS process (`process.env.X =`), inherited by everything spawned after |
| `coding-agent.environment.cleared` | **5** | deleted from a child environment object |

**26 distinct names, 35 memberships**: several names hold more than one role, and collapsing them
loses information. `PI_MODEL` and `PI_PROVIDER` are exposed to tools **and** read by the eval
entry point; `PI_OFFLINE` is read in six places **and** set on this process by `--offline`.

**The write roles are NOT limited to the `PI_` namespace, and one member proves why.** The product
also sets `AI_AGENT=pi` (`cli.ts:14`, `rpc-entry.ts:8`). A prefix-limited scan missed it while this
document listed it in §17, so source and documentation could not close against each other. Reads are
still scoped to the product's own namespace — the same files read some forty terminal and system
variables (`TERM`, `HOME`, `WSL_DISTRO_NAME`, …) which are inputs Pi consumes rather than features it
owns; that boundary is a decision, stated here rather than left implicit.

**Clear-then-set is checked per RECEIVER and per ORDER, and only where it applies.** Two mechanisms
exist, and demanding the same discipline of both produces a false alarm:

| Mechanism | Where | Must clear first? |
| --- | --- | --- |
| **Final map** — the object IS the child environment, seeded from the inherited one (`{ ...getShellEnv() }`) | `core/tools/bash.ts:171-186` | **Yes.** Writes are conditional, so an inherited value would survive one that does not happen |
| **Override map** — a fresh `{}` merged over the inherited environment afterwards, via `inheritEnv` | `server/create-harness.ts:114-118`, applied by `harness/env/nodejs.ts:245-247` | **No.** Assignment already wins |

Comparing name sets globally cannot express either claim: a delete in one file vouched for a write in
another, and a write-then-delete ordering passed. Aggregating per FILE is wrong in both directions —
an unrelated delete elsewhere in the file excuses a write, and a legitimate override that merely shares
a file gets flagged. Pairing by the receiver's TEXT is also wrong, because two functions may each
declare a local `env` and neither is the other.

**The obligation belongs to an OBJECT, and objects are identified by their declaration.**
`tools/ts-env-facts.mjs` resolves every access to the innermost binding that declares its receiver, so
identity is that binding's position. Three scoping rules have to hold for that to be true, and each one
misattributes writes if it does not:

* **parameters, destructured names and catch variables are bindings**, so an inner `env` shadows an
  outer one;
* **a binding shadows its WHOLE scope**, not the part below its declaration — `env.X` written above
  `const env = …` in the same function refers to that binding, so names are hoisted before the body is
  walked rather than registered as traversal reaches them;
* **`var` is function-scoped**, so one declared inside a block is still visible after the block closes,
  while `let`/`const` are not;
* **a `for` header declares a binding too**, in a bare declaration list rather than a statement — a
  scan that matches only statements leaves `for (let env = …)` and `for (const env of …)`
  unregistered, and their writes then resolve outward to whatever else carries the name.

A write is checked against deletes on **that same object** at an **earlier offset**. Whether an object is seeded from the inherited
environment is read from its initialiser, following chains of local bindings.

**Three states, not two.** An object whose seed cannot be classified — spread from a parameter, a
property, or anything else this resolver does not follow — is neither obliged nor exempt: writing to it
**fails the run**, because unknown is not exemption. An access whose receiver cannot be resolved to a
binding at all is counted as a member and **explicitly not spoken for**; the emitted authority line
carries how many such accesses exist, so the limit is visible rather than implied.

**Why a literal grep cannot close this axis — three separate reasons, each of which yields a wrong
figure.**

1. **No left token boundary.** `PI_[A-Z_]+` matches inside other identifiers: `ANTHROPIC_API_KEY`
   contains `PI_KEY`, and `CLOUDFLARE_API_HOST` contains `PI_HOST`. **`PI_HOST` is not a Pi
   variable**; it exists only as a substring. A match without a boundary invents members, and prose
   quoting those matches carries the invention forward even after the scan is fixed.
2. **Two names are not literals at all.** `config.ts` builds them from the configurable app name:

   ```ts
   export const ENV_AGENT_DIR   = `${APP_NAME.toUpperCase()}_CODING_AGENT_DIR`;
   export const ENV_SESSION_DIR = `${APP_NAME.toUpperCase()}_CODING_AGENT_SESSION_DIR`;
   ```

   `APP_NAME` comes from `package.json`'s `piConfig.name`, default `pi`, so **the prefix is
   rebrandable**: a fork named `tau` reads `TAU_CODING_AGENT_DIR`. They are recorded at their default
   `pi` spelling, and the extractor reads the derivation rather than hardcoding the pair, so a change
   to the rule is an error rather than a stale entry. **A port that hardcodes `PI_` breaks
   rebranding silently.**

   `packages/tui/src/tui.ts:366` is the exception worth knowing: it reads the **literal**
   `PI_CODING_AGENT_DIR` and falls back to a literal `~/.pi/agent`, because the TUI package does not
   depend on the coding-agent's config. Under a rebrand the TUI and the agent disagree about both.
3. **There are four read forms, not one.** `process.env.X`, `process.env["X"]`, and a member of an
   **injected** `env` object — including via `getProviderEnvValue("X", env)`. Scanning only
   `process.env.X` missed `PI_TUI_ESC_TIMEOUT` (`packages/tui/src/terminal.ts:113`) and
   `PI_CACHE_RETENTION` (three provider APIs), **both of which are documented**.

**What is excluded, and why** — stated because each exclusion is a judgement, not a gap:

| Excluded | Reason |
| --- | --- |
| `PI_CODING_AGENT` | **Assignment only.** Set in `cli.ts:13` and `rpc-entry.ts:7` as a marker for child processes, never read back, so it is not a configuration input. The `(?!\s*=[^=])` lookahead in each read pattern excludes it; `===` comparisons still count |
| `PI_NODE_ENV_EXPLICIT_TEST` and siblings | Test-only, and `test/` is outside the authority |
| `PI_TUI_WIN32_TOOLCHAIN` | **Real, but a build-time selector** read in `packages/tui/native/win32/build.mjs:213` — a build script, not product source. Named here so the boundary is visible rather than silent |

**Documentation comparison, in both directions.** `docs/environment-variables.md` has 17 table rows,
15 of them `PI_*`.

* **Documented but not read: 3** — `PI_SESSION_ID`, `PI_SESSION_FILE`, `PI_REASONING_LEVEL`. These are

* **Read but not documented: 9.** Counted from the sets rather than transcribed, so the number and the

| --- | --- |

## 23. Session hooks — replacement is a lifecycle, not a pointer swap

**Coverage: `semantics-needed`.** Payloads and return contracts are recorded below, but `preparation`
and `branchEntries` are recorded as schemas in §25.4a and §25.4b, so this group is closed for
schemas; behaviour detail is tracked separately.

Evidence: `packages/coding-agent/docs/extensions.md:388-519`.

| Feature ID | Fires | Payload | Cancellable |
| --- | --- | --- | --- |
| `extension.hook.session-start` | session started, loaded or reloaded (:392) | `reason` ∈ `startup`/`reload`/`new`/`resume`/`fork`; `previousSessionFile` for the last three | no |
| `extension.hook.session-info-changed` | display name set via `/name`, RPC or the API (:404) | `name`, or `undefined` when cleared | no |
| `extension.hook.session-before-switch` | before `/new`, `/resume` or `/import` (:415; import via `agent-session-runtime.ts:361-395`) | `reason` ∈ `new`/`resume` — import reports `resume`; `targetSessionFile` for resume | **yes** — `{ cancel: true }` |
| `extension.hook.session-before-fork` | `/fork` or `/clone` (:434) | `entryId`; `position` = `before` for fork, `at` for clone | **yes** — also `skipConversationRestore` (`types.ts:1112-1115`) |
| `extension.hook.session-before-compact` | before compaction (:451) | `preparation`, `branchEntries`, `customInstructions`, `reason`, `willRetry`, `signal` | **yes** — and may **supply the whole `compaction` result** (`types.ts:1117-1120`) |
| `extension.hook.session-compact` | after compaction (:451) | `compactionEntry`, `fromExtension`, `reason` ∈ `manual`/`threshold`/`overflow`, `willRetry` (`extensions/types.ts:604-613`) | no |
| `extension.hook.session-before-tree` | before `/tree` navigation (:484) | `preparation`, `signal` | **yes**; may supply `summary` (with `details`, `usage`), and override `customInstructions`, `replaceInstructions`, `label` (`types.ts:1122-1135`) |
| `extension.hook.session-tree` | after tree navigation (:484) | `newLeafId`, `oldLeafId`, `summaryEntry`, `fromExtension` | no |
| `extension.hook.session-shutdown` | before a session runtime is torn down (:507) | `reason` ∈ `quit`/`reload`/`new`/`resume`/`fork`; `targetSessionFile` | no |

### 23.1 The replacement sequence — the part a port would get wrong

`/new`, `/resume`, `/fork`, `/clone` **and `/import`** do **not** mutate the current session in place.

`importFromJsonl()`
(`core/agent-session-runtime.ts:361-395`, called from `interactive-mode.ts:5879,5892`) runs the same
replacement: it fires `session_before_switch`, is cancellable, tears the old runtime down, binds a
new one, and emits `session_start` with `reason: "resume"`. Listing four variants understated the
surface by one. Pi runs a
full teardown and rebind (:432-433, :450-451):

1. `session_before_*` fires and **may cancel**;
2. `session_shutdown` fires for the **old** extension instance;
3. extensions are **reloaded and rebound** for the new session;
4. `session_start` fires with the reason and `previousSessionFile`.

The documentation states the contract for extension authors directly: clean up in
`session_shutdown`, re-establish in-memory state in `session_start`. **A port that swapped session
state behind a still-live extension instance would satisfy no part of this**, and would do so
silently — the extension would keep stale in-memory state with no signal that its world changed.

### 23.2 This explains the `cancelled` flags found earlier

Four RPC responses carry `{ cancelled }` (§21.2): `new_session`, `switch_session`, `clone`, `fork`.
Those are exactly the operations fronted by a cancellable hook. So "succeeded, having deliberately
done nothing" is not a UI quirk — **an extension can veto the operation**, and the RPC contract
propagates that as success-with-cancelled rather than as an error.

Compaction and tree navigation are cancellable too, and `session_before_tree` can go further by
**supplying its own summary** in place of the one Pi would generate.

### 23.3 Still open in this group

`session_before_compact`'s `preparation` and `branchEntries`, and `session_before_tree`'s
`preparation`, are expanded in §25.4b. Compaction's own document
is now read into the census (§25); branch summarization within it is not.


## 24. Remaining hooks — model, bash, input, startup, resources

Evidence: `packages/coding-agent/docs/extensions.md`.

| Feature ID | Fires | Return contract |
| --- | --- | --- |
| `extension.hook.model-select` | model changes via command, cycling, **or session restore** (:713) | notification; `source` ∈ `set`/`cycle`/`restore` |
| `extension.hook.thinking-level-select` | thinking level changes (:734) | **notification only — return values ignored** |
| `extension.hook.user-bash` | user runs `!` or `!!` (:852) | **can intercept** — replace operations, wrap the built-in, or return the result outright |
| `extension.hook.input` | user input received (:884) | `continue` / `transform` / `handled` |
| `extension.hook.project-trust` | before trusting a project with dynamic config (:352) | `{ trusted: "yes"｜"no"｜"undecided", remember? }` |
| `extension.hook.resources-discover` | after `session_start` (:371) | contributes `skillPaths`, `promptPaths`, `themePaths`; `reason` ∈ `startup`/`reload` |

### 24.1 Input has a five-step order, and the hook is not first

`extensions.md:888-893` states it explicitly:

1. **extension commands** (`/cmd`) are matched first — and if one matches, **the `input` event never fires**;
2. `input` fires — may intercept, transform, or handle;
3. otherwise skill commands (`/skill:name`) expand;
4. otherwise prompt templates expand;
5. agent processing begins.

So the hook sees **raw text**: `/skill:foo` and `/template` are *not yet expanded*. Two consequences
a port must preserve: an extension command silently pre-empts the hook entirely, and a handler
inspecting input cannot assume expansion has happened.

Result semantics (`:928-931`): `transform` **chains across handlers**, while `handled` is
**first-wins** and skips the agent completely. `source` ∈ `interactive`/`rpc`/`extension`, and
`streamingBehavior` is `undefined` when idle, `steer` mid-stream, `followUp` when queued — the same
distinction recorded for the RPC commands.

### 24.2 Bash execution is fully replaceable

`user_bash` is not an observation point. A handler may supply its own operations (the documented
example is SSH, i.e. running the user's shell commands **on another machine**), wrap the built-in
backend, or return a result directly without executing anything.

This is a larger capability than the name suggests: it means the shell backend is a **seam**, not a
built-in. pi-go currently has no equivalent — its bash tool would be a fixed local implementation.

### 24.3 Project trust is a first-decision-wins protocol

`project_trust` runs during startup and again when session replacement enters a cwd whose trust is
unresolved. Only **user/global and CLI `-e` extensions participate** — project-local extensions are
deliberately not loaded until trust is resolved, which is the point of the hook.

Resolution order: the first handler returning `yes`/`no` **owns the decision and suppresses the
built-in prompt**; `remember: true` persists it, otherwise it lasts for the process; `undecided`
defers to later handlers, then to saved decisions, then to the `defaultProjectTrust` setting.

The context passed here is **deliberately reduced** — cwd, mode, hasUI and the UI helpers only —
because the full session context does not exist yet.

### 24.4 `model_select` fires on restore, not just on user action

`source: "restore"` means resuming a session re-emits the selection. A port treating this hook as
"the user changed the model" would fire the wrong behaviour on every resume. This is separate from
`model_changed`, which pi-go must emit itself and which eino does not provide.

### 24.5 Hook axis status

Names and return contracts are now recorded for **every** hook group, and the two typed preparation
payloads are expanded in §25.4b. Still `schema-needed`: per-hook payload field lists beyond what the
documentation shows.


## 25. Compaction — additive, and it confirms the truth/projection split

Evidence: `packages/coding-agent/docs/compaction.md`. This closes the gap §23.3 left open.

### 25.1 Compaction does not delete anything

A compaction appends a `CompactionEntry` carrying a summary and a `firstKeptEntryId`; the session
then **rebuilds the context** for the next request as *summary + entries from `firstKeptEntryId`
onward* (:39-46). The summarized entries remain in the session.

**This is Pi confirming, rather than pi-go assuming, the distinction its session package is built
on.** Compaction changes the *projection* handed to the model; it does not edit truth. A port that
implemented compaction by removing messages would lose history that Pi keeps, and would do so
invisibly — the model's next request would look identical.

### 25.2 Trigger and cut point

| Rule | Value |
| --- | --- |
| Auto-trigger | `contextTokens > contextWindow - reserveTokens` (:31) |
| `reserveTokens` default | 16384, configurable per user or per project (:35) |
| Cut point search | walk **backwards** from newest, accumulating token estimates until `keepRecentTokens` is reached (:41) |
| `keepRecentTokens` default | 20000, configurable (:41) |
| Manual | `/compact [instructions]`, where instructions focus the summary (:37) |
| Iteration | the **previous summary is passed as context** when present (:43) |

### 25.3 A hard invariant: never cut at a tool result

Valid cut points are user, assistant, BashExecution and custom messages
(`custom_message`, `branch_summary`). **Tool results are never valid cut points — they must stay with
their tool call** (:111-117).

That is the same pairing invariant recorded for unmatched tool calls, appearing in a second
mechanism: a cut that separated a call from its result would produce a context containing a tool call
with no result, i.e. the corrupt state that cancellation handling exists to represent honestly. A
port that chose cut points by token budget alone would hit this.

**This does not mean cuts land only between turns.** `CompactionPreparation.isSplitTurn` exists
because the cut point CAN fall inside a turn; when it does, the part of the turn before the cut is
summarised separately as `turnPrefixMessages`, so one turn contributes to two summaries. Reading
"never cut at a tool result" as "always cut between turns" drops that second list.

### 25.4a TWO session entry models, sharing discriminants and not shapes

`branchEntries` was recorded as a type name; resolving it to `SessionEntry[]` turned up a larger
finding. There are **two entry unions in two packages**, and they are not the same set:

| | `coding-agent.session-entry.*` | `agent-harness.session-entry.*` |
| --- | --- | --- |
| Authority | `core/session-manager.ts` `SessionEntry` | `agent/src/harness/session/types.ts` `Entry` |
| Members | **9** | **7** |
| Only here | `label`, `session_info` | `active_tools_change` |
| Shared | `message`, `model_change`, `thinking_level_change`, `compaction`, `branch_summary`, `custom` | same six |

⚠️ **`compaction` is the dangerous one: same discriminant, different fields.** The coding-agent's
`CompactionEntry` carries `firstKeptEntryId` — a boundary pointer into the entry list. The harness's
carries `retainedTail: AgentMessage[]` — the retained messages **inline**. Both are `type:
"compaction"`. A port that reads one shape and writes the other produces sessions whose discriminants
all validate and whose content is wrong.

One name covering two sets recurs in this codebase: the two tool sets,
the two protocols and the three `ThinkingLevel` declarations. The pattern is now expected rather than
surprising: **check whether a name means one thing before treating it as one member set.**

`SessionStopReason` in the harness is a related case, but computed rather than duplicated:
`Exclude<StopReason, "pending"> | "deferred"`. A port must derive it from the base union, because
copying the base set gives one member too many.

`agent-harness.compaction-reason.*` is emitted alongside — `manual`, `threshold`, `overflow`. Three
distinct triggers, and only the first is user-initiated; the census records the overflow path as the
one that may retry the interrupted turn.

### 25.4b Three payload schemas, by field

**`CompactionPreparation`** (`core/compaction/compaction.ts:692-708`) — the payload an extension
receives before compaction, and the reason it can substitute its own summary:

| Field | Meaning |
| --- | --- |
| `firstKeptEntryId` | the linear boundary — real entries resume here |
| `messagesToSummarize` | what will be summarised and dropped from the projection |
| `turnPrefixMessages` | **the earlier part of a split turn**, summarised separately |
| `isSplitTurn` | whether the cut fell inside a turn |
| `tokensBefore` | context size before compaction |
| `previousSummary?` | the prior summary, **fed back in** so compaction is iterative |
| `fileOps` | file operations extracted from the messages being summarised |
| `settings` | the compaction settings in force |

`previousSummary` and `fileOps` are the two fields that make this accumulative rather than
memoryless. A port that omits `previousSummary` produces a correct-looking first compaction and loses
everything before it on the second.

**`TreePreparation`** (`core/extensions/types.ts:624-636`) — the branch-summarisation counterpart,
addressed by tree position rather than a linear boundary:

| Field | Meaning |
| --- | --- |
| `targetId` / `oldLeafId` / `commonAncestorId` | the destination, the previous leaf, and where the two paths meet (the last two nullable) |
| `entriesToSummarize` | the entries on the abandoned path |
| `userWantsSummary` | **the user's choice, carried in the payload** — not something the extension infers |
| `customInstructions?` | extra instructions for the summariser |
| `replaceInstructions?` | when true, `customInstructions` **REPLACES** the default prompt rather than appending |
| `label?` | label attached to the resulting branch-summary entry |

`replaceInstructions` is a seam, not a convenience: an extension can discard Pi's summarisation prompt
entirely. A port that only ever appends silently reduces what extensions can do.

**`Usage`** (`ai/src/types.ts:370-391`) — and it cannot be summed naively:

| Field | Note |
| --- | --- |
| `input` / `output` / `cacheRead` / `cacheWrite` | the four token counts |
| `cacheWrite1h?` | **a SUBSET of `cacheWrite`** (1-hour retention); Anthropic only |
| `reasoning?` | **a SUBSET of `output`** — `output` already includes it |
| `totalTokens` | reported alongside, not derived here |
| `cost` | parallel breakdown with its own `total` |

⚠️ **Both optional fields are subsets, so adding them to their parents double-counts.** And
`undefined` is not `0`: providers that expose a breakdown set a number, possibly zero, while providers
that do not leave it absent. A port defaulting to `0` destroys the distinction between "the provider
reported none" and "the provider does not report this".

`StopReason` beside it is a closed 7-member union, emitted as `ai.stop-reason.*`: `pending`, `stop`,
`length`, `toolUse`, `error`, `aborted`, `deferred`. `pending` and `deferred` are the two a port is
likely to omit, and both are states rather than terminations.

### 25.4 `CompactionEntry` — schema recorded

| Field | Meaning |
| --- | --- |
| `type` | `"compaction"` |
| `id` / `parentId` / `timestamp` | entry identity and position |
| `summary` | the summary text |
| `firstKeptEntryId` | boundary from which real entries resume |
| `tokensBefore` | context size prior to compaction |
| `usage?` | LLM usage that produced the summary — **counted into session totals** |
| `fromHook?` | true when an extension supplied the summary (documented as a legacy field name) |
| `details?` | implementation-specific; the built-in stores `readFiles` and `modifiedFiles` |

`usage` being recorded matters for the earlier warning about compaction cost accounting: summarization
work is **charged to the session**, and extension-provided summaries store it too when available.
`details` is free-form JSON, so an extension's compaction can carry its own structure.

Branch summarization (`BranchSummaryEntry`, cumulative file tracking) is documented at :148-214 and
**not yet read into this census**. The summary *format* sections (:215-240) are also unread.


## 26. Branch summarization and the shared summary format

Closes the gap §25.5 left open. Evidence: `docs/compaction.md:148-240`.

### 26.1 Branch summarization is a second summarizer, on the session TREE

Triggered by `/tree` navigation away from a branch: Pi offers to summarize the work being abandoned
and injects that context into the branch being entered (:152).

Mechanism (:154-160): find the **deepest common ancestor** of old and new positions · walk from the
old leaf back to it · include messages newest-first up to a token budget · summarize · append a
`BranchSummaryEntry` **at the navigation point**.

So the abandoned branch is left intact and the summary lands on the *target* branch as its new leaf.
Like compaction, this is additive — nothing on the old branch is rewritten.

### 26.2 `BranchSummaryEntry`

| Field | Meaning |
| --- | --- |
| `type` | `"branch_summary"` |
| `id` / `parentId` / `timestamp` | entry identity and position |
| `summary` | the summary text |
| `fromId` | the entry navigated **from** |
| `usage?` | LLM usage that produced it — counted into session totals |
| `fromHook?` | true when an extension supplied it (documented as a legacy field name) |
| `details?` | implementation-specific; built-in stores `readFiles`, `modifiedFiles` |

Structurally parallel to `CompactionEntry`, differing in `fromId` (a tree position) where compaction
has `firstKeptEntryId` (a linear boundary) — the two summarizers answer different questions.

### 26.3 File tracking ACCUMULATES across summaries

Both summarizers extract file operations from the messages being summarized **and from the previous
compaction or branch-summary `details`** (:179-186).

**This is the part a port would most plausibly get wrong.** The naive implementation derives
`readFiles`/`modifiedFiles` from the current window only, which looks correct on a first compaction
and then silently loses history on the second — and across nested branch summaries. The field is
cumulative by design, so that the full record of what has been read and modified survives repeated
summarization.

### 26.4 One shared summary format, and it is prescriptive

Both summarizers emit the **same** structured Markdown (:215-240): `## Goal` ·
`## Constraints & Preferences` · `## Progress` with `### Done` / `### In Progress` / `### Blocked` ·
`## Key Decisions` (decision in bold, then rationale) · `## Next Steps` (numbered).

This is a contract, not a style suggestion: it is what a later summarization consumes as its
"previous summary" input, and what a user reads after a compaction. A port emitting free-form prose
would still function while degrading iterative summarization, since each round would have less
structure to build on than the original guarantees.

### 26.5 Compaction axis status

Closed for both summarizers: triggers, mechanism, cut/ancestor rules, entry schemas, cumulative
tracking and the shared output format. Recorded in §25.4a/§25.4b: the `preparation` and

### 27.2 Session file format and tree — `coding-agent.session.*`, C5

Authority `src/core/session-manager.ts`.

- **File**: JSONL. First line a `SessionHeader` (`:32`) — `type:"session"`,
  `version`, `id`, `timestamp`, `cwd`, optional `parentSession`. Then
  `SessionEntry` lines (`:144`), a nine-member union sharing
  `SessionEntryBase{type,id,parentId,timestamp}` (`:46`).
- **Path on disk**: `<agentDir>/sessions/--<cwd with the leading separator
  stripped and `/`, `\`, `:` replaced by `-`>--/<timestamp with `:` and `.`
  replaced by `-`>_<sessionId>.jsonl` (`:476-489`, `:953`).
- **The conversation is a path, not the file**: `buildSessionPath` (`:334`)
  walks `parentId` from a leaf to the root and reverses. `leafId === null`
  yields an empty path; an absent leaf defaults to the LAST entry in the file.
- **Branching**: continuing after moving the leaf writes new entries with
  `parentId` = that leaf, so the abandoned entries stay in the file and remain
  reachable by leaf id.
- **Fork/clone**: `createBranchedSession` (`:1412`) copies the path to a leaf
  into a NEW file, re-chaining `parentId` after dropping label entries, with
  `parentSession` pointing at the origin. The original file is untouched.
- **Discovery**: `findMostRecentSession` (`:635`) takes the newest `.jsonl` by
  mtime whose header cwd matches, skipping unreadable files.
- **Name**: `getSessionName` (`:1150`) walks entries in REVERSE and returns the
  first `session_info` entry's trimmed name — so the latest wins and an empty
  name clears the title.

**Field shapes for all nine members are now recorded in §21.3** (read 2026-09-04),
including the `label`, `branch_summary`, `custom` and `custom_message` entries
this line previously listed as unread.

**Still not read:** the re-chaining rules that drop label entries on fork in
full, and migration between session versions. Both are behaviour rather than
shape, which is why expanding the entry union did not close them.

### 27.4 Compaction — supplements §25

Authority `src/core/compaction/compaction.ts`.

- **Token estimate** (`:266`): `ceil(chars/4)`, over user content and, for an
  assistant message, text + thinking + each tool call's name and
  `JSON.stringify(arguments)`.
- **Valid cut points** (`:351`): indices of context-visible user-like or
  assistant messages. Never a tool result — it must follow its call.
- **Cut selection** (`:403`): walk back from the end accumulating estimated
  tokens; at `keepRecentTokens`, take the first cut point at or after that
  index; then scan back over adjacent entries that contribute no context
  messages; a cut entry that does not start a turn makes it a SPLIT turn, whose
  prefix is summarised separately by `TURN_PREFIX_SUMMARIZATION_PROMPT`
  (`:795`).
- **Preparation** (`:710`): returns nothing when the last path entry is already
  a compaction; a previous compaction sets the boundary start to its
  `firstKeptEntryId`, and its summary becomes `previousSummary`.
- **Prompts**: `SUMMARIZATION_PROMPT` (`:467`) asks for a fixed section
  structure — Goal, Constraints & Preferences, Progress (Done / In Progress /
  Blocked), Key Decisions, Next Steps, Critical Context.
  `UPDATE_SUMMARIZATION_PROMPT` (`:500`) is used when a previous summary exists
  and instructs preservation. The conversation is serialised to text and wrapped
  in `<conversation>` tags so the model summarises rather than continues it
  (`:649-658`).
- **Defaults** (`settings-manager.ts:13-16`): `keepRecentTokens` 20000,
  `reserveTokens` 16384, `enabled` true.

## Counting discipline

**A convenient proxy is not the authority.** Each count below states the source it is taken from,
next to the proxy that answers the same question with a different number.

| Count | Value | Proxy that disagrees | Authority |
| --- | --- | --- | --- |
| RPC events | **24** | the docs table (21/22) | source union of `AgentEvent` + `AgentSessionEvent` + RPC |
| RPC UI requests | **9** | doc headings (10) | the `RpcExtensionUIRequest` type |
| Providers | **42** | `.ts` filenames (44) | `builtinProviders()` / `builtinImagesProviders()` |
| Harness tools | **4** | `.ts` filenames (6, counting `image`) | `index.ts` exported creators |

The rule holds only when it is executed as a check against each finished section: a reading can
satisfy itself that it is already following the rule while counting the proxy.

**Rules this imposes on the rest of the census:**

1. **Enumerate from the source union first.** Docs are a two-way cross-check, never the source.
   Docs-derived enumeration cannot find a source-only feature *by construction* — which is exactly
   the omission class this gate exists to catch.
2. **A file listing is not a registry.** If the product has a registration point (`all.ts`,
   a union type, a command table), that is the count. File names are a proxy that silently merges
   implementations, helpers, generated wrappers and test doubles.
3. **State which meaning a number has.** "44 providers" merged four different things. Every count
   here now names its authority.
4. **A count that has not been re-derived from its authority is `semantics-needed`, not a fact.**
